### Main invariants

- WGS84 coordinates are finite and in range;
- at most 32 waypoints and three alternatives in v0;
- consecutive requested stops differ;
- route geometry contains at least two points;
- legs cover one contiguous geometry range;
- leg endpoints equal referenced geometry points;
- maneuver locations equal their geometry indices;
- route distance and duration equal checked leg totals;
- route IDs in one success result are unique;
- provenance is explicit and bounded;
- `NoRoute` and `InvalidRequest` are not retryable for an unchanged request;
- diagnostic strings and metadata collections are bounded.

## Completed — request/result postcondition

Added:

```kotlin
RoutePlan.requireMatches(request)
```

The function verifies that a canonical route has exactly one leg for every
requested segment:

```text
origin -> waypoint 1
waypoint 1 -> waypoint 2
...
last waypoint -> destination
```

This closes a subtle gap: checking only route origin and destination would allow
an adapter to ignore one or more waypoints while still returning a superficially
valid route.

## Completed — defensive immutability

The first code version used read-only Kotlin collection interfaces but accepted
caller-owned lists and sets directly. A caller could pass a mutable collection,
mutate it after construction, and invalidate an already validated object or a
map key.

The contracts now create snapshots for:

- plugin capabilities;
- runtime platforms;
- license notices;
- route waypoints;
- maneuvers;
- geometry;
- legs;
- provenance data sources;
- successful alternative routes.

Collection-bearing canonical types are regular immutable classes with explicit
equality and hash code rather than data classes that retain mutable inputs.
Regression tests mutate the original collections after construction and verify
that the contracts remain unchanged.

```kotlin
    suspend fun plan(request: RouteRequest): RoutePlanningResult

```

Design decisions:

- expected provider outcomes use a canonical sealed result;
- provider exceptions and JSON types do not cross the boundary;
- coroutine cancellation must propagate normally;
- the port is asynchronous even though the first fake completes immediately;
- capability selection is separate from provider identity.

## Completed — deterministic fake provider

Added:

```text

```

`FakeRoutePlanner`:

- performs no network or file I/O;
- matches immutable requests exactly;
- returns declared canonical routes;
- records calls for application tests;
- returns canonical `NoRoute` on a catalog miss;
- validates route/request waypoint correspondence during construction;
- validates provenance against its plugin ID;
- declares deterministic, offline, alternatives and maneuvers capabilities.

The fake deliberately does not calculate a route. Route calculation belongs to
the Java/Rust reference implementation or future real providers.

## Review findings

### Review round 1 — mutable collections

Finding:

- Kotlin `List` and `Set` are read-only interfaces, not guaranteed immutable
  values;
- a provider could retain and mutate the original collection after contract
  validation;
- mutable `RouteRequest` internals could also corrupt fake-provider map keys.

Fix:

- defensive snapshots at every canonical collection boundary;
- explicit equality/hash code for collection-bearing classes;
- regression tests for post-construction mutation.

### Review round 1 — ignored waypoints

Finding:

- the first provider probe verified only origin and destination;
- a route could ignore requested waypoints and still pass.

Fix:

- `RoutePlan.requireMatches(request)`;
- one canonical leg per requested segment;
- fake-constructor validation;
- contract-probe validation;
- regression test for a route that ignores a waypoint.

### Review round 2 — source set confused with runtime platform

Finding:

- `kotlin.common` was initially listed as a supported plugin platform;
- common code is compiled into runtime targets and is not an execution
  environment.

Fix:

- platform IDs now describe runtime environments only;
- fake descriptor declares JVM and Linux x64;
- documentation distinguishes shared source from runtime deployment.

### Review round 2 — unbounded metadata

Finding:

- waypoint, capability, platform, license, provenance and diagnostic metadata
  were structurally valid but not bounded;
- a provider boundary should not accept arbitrarily large control metadata.

Fix:

- explicit v0 maxima;
- validation and regression tests;
- route geometry itself is not given an arbitrary low limit because real routes
  can legitimately contain many points; performance limits require separate
  evidence.

## Architectural decisions made autonomously

1. Introduce Kotlin Multiplatform only when the first genuinely shared contract
   exists.
2. Keep Java/Rust reference models separate from canonical application models.
3. Use a generic plugin SDK shared by future provider families.
4. Model expected failures explicitly and let cancellation propagate.
5. Use exact deterministic catalog matching in the fake.
6. Define one canonical leg per requested stop segment.
7. Snapshot caller/provider collections at the contract boundary.
8. Bound control metadata while deferring evidence-based geometry limits.
9. Treat supported platforms as runtime environments, not source sets.
10. Keep the Gradle Wrapper as explicit debt rather than generating an
    unverifiable binary through ad-hoc means.

These decisions are reversible and remain inside the accepted architecture.
